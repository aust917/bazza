# Baseline существующей записи Hark

Дата: 2026-10-30 · Статус: план подготовлен; аппаратная запись не начиналась.
Основа: текущие исходники `917e2a0` и локальная документация; production capture-код
не меняется. Связи: [ТЗ R1–R2/R6/R9](../../product/requirements.md),
[roadmap, этап 0](../plans/2026-10-30-local-fork-roadmap.md), [сборка и тесты](../testing.md).
[Результаты подготовки](../test-reports/2026-10-30-baseline.md) фиксируются отдельно.

Цель — узнать, как приложение работает сейчас, и получить материал для сравнения
последующих изменений. Наличие дефекта синхронизации заранее не предполагается.
Frontend typecheck, UI-тесты и сборка полезны, но не доказывают работу desktop capture.

## Условия начала

- Подготовка изолированного локального toolchain/build разрешена. Запись микрофона
  и экрана выполняется только после отдельного сигнала пользователя.
- Нужна запускаемая desktop-сборка именно проверяемых исходников, реальные ffmpeg/
  diarization sidecars и native runtime libraries. Browser mock не подходит.
- Сначала сохраняются текущие настройки: устройства, режим audio scope, экран,
  FPS, размер и параметры кодирования. При пустых настройках код задаёт 15 FPS,
  max-height 1080, libx264/veryfast/CRF 28; фактические значения нужно проверить.
- В контрольном прогоне не менять defaults и механизм записи. Новый профиль качества
  сравнивать с этим результатом отдельно, после проверки существующего поведения.
- Использовать подготовленный экран и синтетическое локальное медиа; скрыть личные
  окна/уведомления. Для микрофона — выбранный тестовый input или намеренная тестовая
  реплика пользователя. Случайный звук комнаты не является контрольным материалом.
- Для первого прогона достаточно захвата и воспроизведения; модели/транскрипцию
  проверять отдельным прогоном с зафиксированными доступными локальными моделями.
  В тестовых settings отключить `auto_update_check` и внешние интеграции, оставить
  локальный backend; календарные URL, webhook и LAN-share для baseline не включать.

## Отдельная библиотека

Смена Tauri identifier или переменной APPDATA не гарантирует изоляцию: путь выбирает
`hark-store::data_dir()`. Перед запуском остановить все Hark и установить, какой
каталог/`data-dir.txt` используется сейчас, не считывая содержимое личных встреч.

1. Сохранить точные исходные байты pointer-файла либо факт его отсутствия.
2. Создать отдельный пустой каталог теста и направить pointer на него до запуска.
   Целевой каталог должен существовать, иначе `data_dir()` вернётся к default.
3. Убедиться по стартовому логу/`data_info`, что Store открыт в тестовом каталоге,
   и настроить только тестовые источники/локальную обработку.
4. После выхода из всех тестовых процессов восстановить исходный pointer и проверить
   возврат обычной библиотеки. Саму пользовательскую БД не мигрировать ради теста.

UI-команда `change_data_dir` копирует всю текущую библиотеку и записывает pointer
для следующего запуска; она не создаёт пустую изолированную библиотеку. Альтернатива —
отдельный локальный OS test account. Не запускать одновременно обычный и тестовый Hark.

## Контрольный источник и измерения

Использовать локальный заранее сформированный ролик с повторяемыми вспышками,
синхронными щелчками и видимым номером/временем маркера. Это даёт одну временную
основу исходного аудио и изображения. Для микрофона нужен отдельный различимый
сигнал/тестовая реплика; не выдавать system-only проверку за проверку микрофона.

Для каждого маркера записывать `Δ = t_audio − t_video` в миллисекундах и изменение
`Δ_end − Δ_start`. Фиксировать номер кадра и фактический output FPS; при 15 FPS
один кадр занимает около 66,7 мс. Сначала сохранять числа и наблюдаемое поведение.
Длительность длинного прогона и критерии оценки определить отдельно; заранее
назначенного порога, автоматически означающего дефект, в этом плане нет.

## Матрица прогона

| ID | Сценарий | Что наблюдать и сохранить |
| --- | --- | --- |
| B0 | Запуск, список устройств/экранов, текущие settings | Версия/сборка, фактический data dir, выбранные источники, defaults, состояние окна/record bar |
| B1 | Короткие проверки mic, system, затем обоих | Различимые сигналы в mic/sys/mix, фактический audio scope и endpoint; output другого устройства проверять отдельно |
| B2 | Около 2 минут экран + оба аудиоисточника без пауз | Выбранный экран, начало/середина/конец маркеров, Δ и drift, свойства файлов, корректная остановка |
| B3 | Тот же источник, известные моменты pause/resume | Состояния UI, какие интервалы попали в каждый поток, порядок маркеров и Δ до/после паузы; сначала описать факт |
| B4 | Длинный непрерывный прогон, длительность задаётся перед тестом | Начало/конец и промежуточные Δ, пропуски, размер/CPU/RAM, stop и пригодность итогового файла |
| B5 | Повторное открытие и перезапуск | Запись в библиотеке, audio/video playback, seek, доступность исходных дорожек |

Испытания переключения устройств, потери ffmpeg и аварийного восстановления проводить
после базового прогона в той же тестовой библиотеке, без изменения захвата. Для каждого
проверяемого наблюдения достаточно одного изменённого условия относительно baseline.

## Доказательства и решение

В локальном отчёте: дата, исходная версия/сборка, OS, devices и audio scope, settings,
тестовый источник, шаги, длительность, наблюдаемое поведение, измерения и ограничения.
Файлы записи/кадры/логи сохранять локально вне отслеживаемого исходного дерева;
результаты записывать без содержимого личных встреч. Не делать push/PR/remote CI.

Возможные итоги: «поведение подтверждено», «гипотеза не воспроизведена» или
«недостаточно данных». Если обнаружено отклонение, повторить его на том же материале
и только затем создать отдельную задачу: ожидаемое поведение, фактический результат,
шаги воспроизведения и минимальный объём исправления. Если текущая запись работает
приемлемо, сохранить её и отдельно решать задачу UI-настроек качества.

## Ограничения существующего smoke

`src-tauri/src/smoke.rs` пишет 8 секунд с текущими audio settings, в обычную библиотеку.
Видео включается только через `HARK_SMOKE_VIDEO=1`; пауза не проверяется. Smoke
ожидает `MeetingStatus::Ready`, печатает имеющиеся файлы/текст, но не измеряет A/V
смещение, drift, содержимое дорожек или выбранный экран. Exit code 0 и наличие MP4
не являются доказательством синхронизации. Не запускать smoke до изоляции и сигнала
пользователя на запись.
