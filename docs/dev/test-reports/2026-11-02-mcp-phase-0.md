# MCP: реализация этапа 0

Дата: 2 ноября 2026 года. Среда: Windows, Rust/Cargo 1.99.1, MSVC.
Владелец интеграции: текущая сессия MCP. [Основной план](../plans/2026-11-02-mcp-implementation.md).

## Изменения

- [Аудит writers](../research/2026-11-02-mcp-writer-audit.md) фиксирует Store constructors,
  DB/settings/file producers, startup/Exit/recovery и zero-write gate.
- [Граница контрактов](../research/2026-11-02-mcp-contract-boundary.md) фиксирует
  имена tools, library grant, роли, revoke, persistent revisions и безопасные DTO;
  полные executable input/output schemas остаются следующей задачей этапа 0.
- [Synthetic test support](../../../crates/bazza-service-test-support/README.md)
  воспроизводит frozen v8 library из SQL/искусственных байтов. Ready/missing/orphan/
  corrupt recordings, RU/EN, raw/manual/empty/automatic overlays, summaries,
  citations, shares, voice memory и provenance проверяются без пользовательских данных.
- [bazza-templates](../../../crates/bazza-templates/src/lib.rs) владеет чистыми builtin
  templates и parser. Шесть файлов перенесены побайтово; ID, порядок и public
  re-export `bazza_llm::summary` сохранены. Будущий сервис может seed templates
  без зависимости от native inference.
- [Lifecycle probe](../../../crates/bazza-service-probe/README.md) читает только
  явно отмеченную synthetic v8 library, не запускает migrations и не ищет default
  data directory. Удерживает canonical fixture lock до закрытия read-only SQLite,
  публикует bounded atomic status и использует instance-bound stop intent.
  Это эксперимент этапа 0, не production service, IPC, grant или MCP adapter.

Capture callbacks, recorder, STT control, pipeline, GUI commands и рабочая библиотека
не менялись этой сессией. Параллельная performance-сессия владеет их изменениями;
они не откатывались и не включаются в выводы о реализации MCP. Install/staging,
запись звука, облачные запросы и изменение настроек Bazza не выполнялись.
Единственная OS-регистрация — временная задача lifecycle experiment; она удалена.

## Проверки

Cargo запускался offline в отдельном target с двумя jobs, без native AI engines
и без конкуренции за target/staging параллельной сборки:

```powershell
cargo test --offline -p bazza-templates -p bazza-service-test-support -p bazza-service-probe -p bazza-store -p bazza-share -p bazza-summary-runner --target-dir .git/local-tests/20261102-mcp/target -j 2
```

Первый прогон: **88 passed**, 0 failed. Store — 56, share — 23, summary-runner — 3,
fixtures — 3, templates — 3. Summary-runner здесь собран из текущих исходников, что
закрывает ограничение cached EXE в [исходном baseline](2026-11-02-mcp-baseline.md).

Проверены создание пустого Store, сохранность исходных v8 полей во всех 16 базовых
таблицах при upgrade/reopen, всех пяти искусственных media artifacts, raw/manual/
empty overlays, rollback/retry imports и corrections, FTS/chunks/vectors, bundle
roundtrip и path bounds, disabled shares и HTTP range, bounded server stop,
fake-CLI cancellation/timeout/output bounds.

UI baseline: **41 passed** в шести целевых файлах; команда и точная граница mocks
описаны в [baseline](2026-11-02-mcp-baseline.md). Это не native capture acceptance.

```powershell
cargo tree --offline -p bazza-service-probe -p bazza-templates --edges normal --prefix none --format '{p}'
```

В runtime dependency graph отсутствуют Tauri, whisper, llama и sherpa.
Это проверка probe/templates, будущие production service/adapter ещё не реализованы.

Дополнительный integration run:

```powershell
cargo test --offline -p bazza-service-probe --test lifecycle --target-dir .git/local-tests/20261102-mcp/target -j 2 -- --nocapture --test-threads=1
cargo clippy --offline -p bazza-service-probe -p bazza-service-test-support -p bazza-templates --all-targets --target-dir .git/local-tests/20261102-mcp/target -j 2 -- -D warnings
```

**9 harness tests passed**, clippy без warnings. Включены отказ без явной fixture,
future schema без миграции, canonical singleton/reopen, byte-identical read-only
run, atomic JSON readers и реальный direct-child stop/restart со старым stop intent.
Два detached tests проверили корректный отказ `DETACHED_LAUNCH_UNAVAILABLE: os error 5`:
этот Windows host запрещает breakaway. Они **не доказали** независимый detached
lifecycle. Две symlink subcases не выполнены: Windows вернул privilege error 1314;
доступный source guard не заменяет будущую native ACL/reparse acceptance.

## Windows lifecycle и решение по launcher

Обычный child spawn не используется как доказательство независимости. На этом
Codex desktop execution host `DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB`
получил `Access denied`. Скрытого fallback к обычному дочернему процессу нет.

Выполнен отдельный
[broker experiment](../../../crates/bazza-service-probe/experiments/windows-user-task.ps1)
с temporary Task Scheduler task текущего интерактивного пользователя, limited
run level, без пароля и повышения прав. Такой logon/run context предусмотрен
[Task Scheduler](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks);
задача запускается on demand, согласно
[RegisteredTask.Run](https://learn.microsoft.com/en-us/windows/win32/taskschd/registeredtask-run).

Команда после генерации отдельной fixture:

```powershell
cargo run --offline -p bazza-service-test-support --example create_v8 --target-dir .git/local-tests/20261102-mcp/target -j 2 -- .git/local-tests/20261102-mcp/task-broker-fixture-reviewed
& ./crates/bazza-service-probe/experiments/windows-user-task.ps1 -ProbeExecutable .git/local-tests/20261102-mcp/target/debug/bazza-service-probe.exe -FixturePath .git/local-tests/20261102-mcp/task-broker-fixture-reviewed -EvidencePath .git/local-tests/20261102-mcp/task-broker-evidence-reviewed.json
```

Результат: **survived_launcher_tree_kill**. После `taskkill /PID <owned launcher> /T /F`
heartbeat того же instance вырос с **13 до 18** и synthetic meeting читалась без GUI.
`task_removed=true`, `cleanup_errors=[]`; повторная проверка не нашла временную
задачу и процесс probe. Readiness привязан к свежему instance UUID в task action;
старый status/чужой владелец fixture не может дать ложную готовность. Повторный
запуск с прежней fixture отдельно отвергнут до регистрации task.
Хеш проверенного EXE: `6466CBC4056C3647800A3344A86C3BA75D04CB7DC8389611E92815C2AE155A7A`.
Evidence JSON и generated library остаются только в ignored `.git/local-tests/20261102-mcp/`.

Для Windows выбран user-session Task Scheduler broker, зарегистрированный при
явной локальной настройке интеграции: InteractiveToken/Limited, без login/boot
trigger, executable с абсолютным путём и public library/connection ID, без token
в arguments; on-demand запуск не принадлежит дереву GUI/adapter. Сначала
проверяется зарегистрированное определение/владелец, затем вызывается запуск,
готовность подтверждается аутентифицированным versioned handshake с bounded timeout.
Сервис сам удерживает canonical library owner guard, а повторный запуск клиента
подключается к существующему владельцу. Если broker не установлен/недоступен —
typed setup/unavailable error, без прямого SQLite/child fallback.

Production broker registration/discovery/auth ещё не реализованы. Experiment
доказывает этот механизм в одном Windows desktop host, а не поддержку всех
версий Codex/Claude Code или поведения после logout. macOS остаётся непроверенным.

`cargo fmt --check` для трёх новых crates, `node scripts/check-docs.mjs` и
`git diff --check` прошли. Native build `bazza-llm`/GUI эта сессия не запускала;
его совместимый re-export должен пройти общую native проверку у интегратора.

## Gate и следующий шаг

Начальный snapshot выше сохраняет проверки подготовки. В следующем increment
завершены [29 executable schemas](../../../crates/bazza-service-api/README.md),
[доступный Windows software/native baseline](2026-11-02-mcp-windows-baseline.md)
и [Windows service skeleton этапа 1](2026-11-02-mcp-phase-1.md). Windows software
gate этапа 0 закрыт в уточнённом пользователем scope. Мocks и ordinary child spawn
не подменяют hardware capture/A-V, macOS и реальную MCP host acceptance.
Stage-3 GUI cutover не выполнен; MCP mutations к рабочей библиотеке не подключены.
Новый lock сам по себе не исключает legacy GUI: нынешний startup открывает Store
до установки single-instance plugin. Cutover требует stopped-owner snapshot и
version interlock, предусмотренные основным планом.
