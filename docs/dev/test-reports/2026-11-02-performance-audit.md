# Аудит производительности Bazza

Последующие исправления и повторные замеры: [результаты](2026-11-02-performance-fixes.md).

Дата: 2026-11-02, Asia/Yekaterinburg. Статус: аудит завершён, новые исправления
в код приложения в рамках аудита не вносились. Проверен текущий рабочий каталог,
включая ранее выполненное исправление аудиоиндикаторов первого запуска.

Область: React UI, Tauri IPC, Store/SQLite, загрузка моделей, фоновые pipeline jobs,
подготовка WAV и диаризация. Сайт и установщики не входили в аудит.
Среда измерений: Windows, Intel Core i7-14700KF, 28 логических CPU, около 64 ГБ RAM;
Node 24.12.0; браузер Chromium 156; Python SQLite 3.50.4.

Пассивный снимок работавшего экземпляра за 10 секунд: native working set 61,6 MiB,
private 28,7 MiB; private всех восьми процессов приложения/WebView — около
299,8 MiB. Суммарный CPU — 14,5% одного логического CPU, или около 0,52% при
нормировании на 28 CPU. Экран, видимость окна и действия пользователя не
нормализовались, поэтому это наблюдение не служит контролируемым idle baseline.
Working set разных процессов не суммируется как уникальная физическая память.

длинных встреч и линейный рост стоимости обновлений транскрипта.

## F1. Истечение snooze может привести к бесконечному ожиданию

Это скрытая ошибка IPC-пути: текущий UI отправляет только `now`/`never` и не
предоставляет кнопку snooze. `snooze_until` изначально равен `None` и не сохраняется.
Без отдельного вызова `snooze` через IPC обычный UI этот сценарий не запускает.

В [detector_loop.rs](../../../src-tauri/src/detector_loop.rs), строки 39–43,
`if let Some(until) = *state.snooze_until.lock()` удерживает временный guard
до конца тела `if let` в Rust edition 2021. После истечения срока тело повторно
захватывает тот же нерекурсивный mutex при присваивании `None`.

Сначала зависает поток обнаружения. Следующий вызов режима `snooze` из синхронного
[dismiss_detection](../../../src-tauri/src/commands/recording.rs), строка 85,
может заблокировать уже главный поток. Условие: обнаружение включено и дошло до
обработки истёкшего snooze.

Отдельное Rust-воспроизведение с `try_lock` подтвердило, что второй lock внутри
тела недоступен, а после выхода из тела доступен. Реальное приложение намеренно
не доводилось до зависания. Исправление: закончить время жизни первого guard до
`if let` либо использовать один именованный guard без повторного захвата.

## F2. Тяжёлые native операции всё ещё блокируют главный поток

После исправления `sample_levels` остаются другие синхронные команды:

- [ai.rs](../../../src-tauri/src/commands/ai.rs), строки 58 и 199: `generate_summary`
  и `send_chat` вызывают `state.llm()` до `thread::spawn`. Холодная загрузка GGUF
  происходит в [state.rs](../../../src-tauri/src/state.rs), строка 192.
  Сценарий повторяется после выгрузки неиспользуемого движка.
- [organize.rs](../../../src-tauri/src/commands/organize.rs), строки 94 и 149:
  экспорт клипа и создание share-клипа синхронно ожидают FFmpeg. Строки 218–252:
  HTML export копирует media, смена каталога делает snapshot и копирование библиотеки.
- [settings.rs](../../../src-tauri/src/commands/settings.rs), строка 59:
  `data_info` рекурсивно обходит recordings/models при открытии настроек.
- [organize.rs](../../../src-tauri/src/commands/organize.rs), строки 128–132:
  выключение последнего share вызывает `h.stop()`. В
  [server.rs](../../../crates/bazza-share/src/server.rs), строки 35–40, `stop`
  делает неограниченный `join`. Graceful shutdown локальной Axum 0.8.9 ждёт
  активные соединения; медленное скачивание media может удерживать UI.

Механизмы подтверждены чтением текущих команд и зависимостей. Холодный LLM,
экспорт и сетевое скачивание не запускались; им не приписывается измеренное
число секунд. Исправление: выполнять всю долгую часть в рабочем потоке,
не удерживая общие guards; остановку сервера отделить от UI с ограниченной
стратегией завершения соединений. Проверка: простая IPC-команда должна отвечать
во время каждой такой операции, включая холодную загрузку модели.

## F3. Параллельная диаризация умножает чтение и память полного WAV

[pipeline.rs](../../../src-tauri/src/pipeline.rs), строки 574–605, передаёт
каждому процессу один полный WAV и отдельные `--start-ms/--end-ms`.
В [main.rs](../../../crates/bazza-diarize-cli/src/main.rs), строки 140–148,
полное чтение и ресемплинг выполняются раньше обрезки. Число процессов выбирается
по CPU и ограничено восемью; на данном CPU верхняя граница — семь.

Измерен настоящий release `bazza-diarize.exe` на синтетическом mono PCM16 WAV:
600 секунд, 48 kHz, 57 600 044 байта. Модели намеренно отсутствовали; выполнение
останавливалось после загрузки WAV на проверке model paths, без inference.

| Запрошенный диапазон | Peak working set | Peak private/commit | Полное время процесса |
| --- | --- | --- | --- |
| Все 10 минут | 275,1 MB | 290,0 MB | 0,278 с |
| Первые 5 минут | 276,1 MB | 291,1 MB | 0,236 с |
| Одна секунда | 275,1 MB | 290,0 MB | 0,238 с |

Диапазон практически не влияет на память читателя. Здесь MB — 1 000 000 байт.
Суммарный одновременный RSS нескольких shards не измерялся; модельные allocations
в таблицу не входят. Для длинного файла механизм повторяется в каждом процессе.

Дополнительно точная функция `read_wav_as_16k_mono` из
[recorder.rs](../../../src-tauri/src/recorder.rs), строки 513–529, вместе с
текущим DSP была извлечена без изменений в optimized Rust harness. Для того же
10-минутного WAV: 3,319 с обработки, peak working set 427,2 MB, private 481,6 MB.
В [pipeline.rs](../../../src-tauri/src/pipeline.rs), строки 536–548, этот путь
повторяется для mic/sys ради RMS с шагом 250 мс. Эти повторные загрузки не
объявляются одновременными пиками памяти.

Исправление: чтение нужного диапазона или единожды подготовленный 16k источник;
потоковая подготовка PCM/RMS без хранения нескольких полных копий. Проверка:
память обработки короткого диапазона не должна расти с длиной остального файла;
результаты и временные метки должны сохраняться.

## F4. Пакетная обработка не ограничена общим бюджетом

[recorder.rs](../../../src-tauri/src/recorder.rs), строки 302 и 325, запускает
отдельный pipeline для каждой незавершённой встречи; строка 475 — после Stop.
[import.rs](../../../src-tauri/src/import.rs), строка 89, делает то же для
каждого импорта. Каждый job дополнительно допускает Whisper и несколько
diarizer-процессов. Бюджет каждого job считается без учёта других jobs.

`retranscribe` в [recorder.rs](../../../src-tauri/src/recorder.rs), строки 500–509,
не исключает статус Processing, поэтому backend также допускает повторную
обработку той же встречи. UI обычно запрещает это действие, но общего admission
контроля в backend нет. Риск особенно заметен при восстановлении после сбоя и
импорте нескольких длинных файлов. Нагрузочный запуск inference не выполнялся.

Исправление: общая очередь с бюджетом CPU/RAM, приоритетом текущей записи и
защитой от повторного задания для одного meeting ID. Проверять ограничение числа
активных jobs при startup recovery, batch import и одновременных командах.

## F5. Позиция плеера обновляет все строки транскрипта

[Player.tsx](../../../app/src/components/Player.tsx), строки 43–48, обновляет
позицию через `onTime`; [Meeting.tsx](../../../app/src/routes/Meeting.tsx),
строка 147, хранит её в состоянии страницы.
[Transcript.tsx](../../../app/src/components/Transcript.tsx), строка 127,
заново обходит все строки, включая SpeakerChip, кнопки коррекции и переводы.
DOM не ограничен видимой областью.

Замер: production React и полные стили текущего приложения в Chromium 156.
Русский синтетический текст, смена говорящего каждые четыре реплики, действия
rename/correction заменены no-op. После warmup выполнено 12 обновлений позиции
внутри одной и той же первой реплики, с принудительным layout. Auto-scroll
отключён. Измерение не включает native IPC, декодирование media и весь Meeting.

| Реплик | Элементов DOM | Первое открытие с layout | Обновление p50 / p95 |
| --- | --- | --- | --- |
| 100 | 1 027 | 8,8 мс | 1,9 / 2,4 мс |
| 1 000 | 10 252 | 89,6 мс | 15,1 / 25,0 мс |
| 3 000 | 30 752 | 242,3 мс | 36,9 / 38,1 мс |
| 5 000 | 51 252 | 413,7 мс | 59,5 / 61,5 мс |

p95 здесь — верхняя выборочная величина из 12 измерений, не статистика долгого
production-сеанса. Затраты возникают даже без смены активной строки. Исправление:
изолировать позицию/подсветку от остального дерева, мемоизировать строки и
ограничить DOM больших транскриптов видимой областью. Проверять raw/clean,
коррекции, имена и переход по timestamp наряду со скоростью.

## F6–F8. Масштабирование библиотеки и поиска

F6: [organize.rs](../../../crates/bazza-store/src/organize.rs), строки 50 и 137,
считает встречи для каждой папки/тега коррелированными подзапросами. Миграции
не дают им индексов `meetings(folder_id)` и `meeting_tags(tag_id)`.
Синтетическая SQLite с восемью настоящими миграциями и точным SQL:

| Данные | Папки: текущая схема / с индексом | Теги: текущая схема / с индексом |
| --- | --- | --- |
| 5 000 встреч, по 100 папок/тегов | 17,346 / 0,159 мс | 25,084 / 0,237 мс |
| 20 000 встреч, по 400 папок/тегов | 270,367 / 0,635 мс | 398,744 / 0,904 мс |

Индексы добавлялись только в синтетическую БД в памяти. EXPLAIN подтверждает
замену повторных scan на index lookup. Это SQL benchmark Python SQLite, без Rust
сериализации и IPC. Native команды синхронны, поэтому их стоимость попадает в
UI-путь. Исправление — новая миграция с индексами и проверкой upgrade, без
перезаписи существующих миграций.

F7: [format.ts](../../../app/src/lib/format.ts), строки 23 и 27, выполняет
локализованное форматирование даты/времени с параметрами на каждой строке.
Текущие функции для 1 000 строк: 69,75 мс; для 5 000: 378,21 мс. Повторное
использование `Intl.DateTimeFormat` в контрольной реализации: 1,56 и 6,57 мс,
вывод совпал. Это Node/ICU microbenchmark, не browser frame timing.

[Library.tsx](../../../app/src/routes/Library.tsx), строки 79–87, перечитывает
встречи, папки и теги на каждом `processing` событии; строки 213–214 снова
форматируют даты при рендере, включая ввод поиска. Фильтрация в
[organize.rs](../../../crates/bazza-store/src/organize.rs), строки 113–115,
сначала загружает все встречи. Исправление: кэшировать форматтеры по языку/
параметрам, добавить SQL-фильтрацию/постраничную загрузку и объединять близкие
reload. Шторм событий в простое не подтверждён: текущие processing события
связаны с этапами и завершением блоков, а не с каждым LLM token.

F8: [vectors.rs](../../../crates/bazza-store/src/vectors.rs), строки 104–123,
держит единственный Store mutex во время чтения всех кандидатов, cosine scoring
и полной сортировки. Nullable OR в scoped SQL мешает index lookup. При 50 000
chunks поиск одной встречи из 80 chunks: 12,083 мс SQL-only; прямой scoped
predicate — 0,079 мс. Поиск по всей библиотеке материализует все 50 000 строк:
93,529 мс SQL-only, без Rust scoring/sort. Возможность ожидания Store со стороны
UI установлена по исходникам, конкурентный native timing не измерялся.
Исправление: отдельный scoped SQL, короткое время жизни mutex, top-k без полной
сортировки; затем измерять необходимость более сложного vector index.

## F9–F10. Дополнительные риски под нагрузкой

F9: [stt_stage.rs](../../../src-tauri/src/stt_stage.rs), строка 151, использует
unbounded очередь PCM для local live ASR.
[live.rs](../../../crates/bazza-asr/src/live.rs), строки 41–53, собирает backlog
перед inference; `MAX_S` запускает commit, но не ограничивает backlog.
[recorder.rs](../../../src-tauri/src/recorder.rs), строка 455, ждёт worker при
Stop. Если live-модель медленнее реального времени, растут задержка и очередь
(16k f32 PCM — около 64 kB на секунду необработанного аудио). Нужны ограничение
очереди предпросмотра и явная стратегия отставания с сохранением timeline;
архивная запись должна продолжаться независимо. Модельный stress не запускался.

F10: [ChatPanel.tsx](../../../app/src/components/ChatPanel.tsx), строки 53 и 134,
обновляет массив и рендерит всю историю на каждый delta/ввод черновика.
[Markdown.tsx](../../../app/src/components/Markdown.tsx), строка 51, повторно
разбирает текст завершённых сообщений. Native
[ai.rs](../../../src-tauri/src/commands/ai.rs), строка 254, отправляет delta
непосредственно из callback. Вспомогательный development SSR benchmark:
100 ответов по ~1 000 символов — 21,36 мс полного рендера, без DOM/layout.
Это не измерение частоты или задержки настоящего streaming-сеанса. Исправление:
мемоизировать завершённые сообщения и объединять delta перед UI-обновлением,
сохраняя текст ответа без потерь.

## Порядок исправлений и границы проверки

1. F2: устранить достижимые из UI пути долгого ожидания и блокирующей работы.
2. F3 и F4: ограничить память на диапазон WAV и общее число тяжёлых jobs.
3. F5–F8: сократить работу каждого playback/reload/search обновления.
4. F1, F9–F10: исправить скрытый IPC deadlock; проверить длительную запись на
   медленной модели и длинный streaming chat.

Ранее измеренное исправление аудиоиндикаторов остаётся отдельным результатом:
средний ответ `recording_status` на первом экране снизился с 361,2 до 1,84 мс.
Нативный замер звука занимал ~419–421 мс, а параллельная простая команда отвечала
за 1,4–2,8 мс до его завершения. Эти числа получены на предыдущем этапе работы,
а не повторным запуском пользовательского приложения во время этого аудита.

В аудите не менялись capture defaults, пользовательская библиотека, настройки,
данные встреч или модели. Работавшее приложение не перезапускалось. Новая запись,
inference и внешние интеграции не запускались. macOS, GPU inference и полный
многопроцессный inference stress остаются непроверенными. Это аудит механизмов
и синтетических границ, а не гарантия задержек любого пользовательского сценария.

Воспроизводимые harness и JSON находятся локально в игнорируемых каталогах
`.git/local-tools/` и `.git/local-tests/20261102-performance-audit/`:
`detector-snooze-lock-lifetime`, `benchmark-store-performance.py`,
`diarize-reader-perf.py`, `wav-preprocess-perf.py`, `performance-ui-audit.mjs`,
`perf-vite.config.mjs`/`perf-web`, `ui-browser-benchmark.json`,
`sample-performance-audit.ps1`/`runtime-processes.json`, `source-manifest.json`
(SHA-256 27 исходных файлов и двух EXE). Production UI harness
собирался через `pnpm exec vite build --config .git/local-tools/perf-vite.config.mjs`
и запускался через `vite preview` на loopback. Browser measurements выполнялись
кнопкой стенда через in-app browser. Исходники приложения не модифицировались;
полный unit/native suite повторно не запускался, поскольку изменялась документация
и изолированные измерительные скрипты.
