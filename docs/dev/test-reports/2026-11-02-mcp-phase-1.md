# MCP: основа сервиса, ownership и private IPC

Дата: 2 ноября 2026 года, Asia/Yekaterinburg. Среда проверки — Windows/MSVC.
Продолжает [этап 0](2026-11-02-mcp-phase-0.md) и
[Windows software baseline](2026-11-02-mcp-windows-baseline.md)
[плана MCP](../plans/2026-11-02-mcp-implementation.md).

Реализован отдельный Tauri-free сервис с private status/metadata read, явной
миграцией artificial library, singleton ownership и Windows demand-start broker.
Он открывает **только явно отмеченные synthetic fixtures**. GUI всё ещё владеет
production Store; общего production owner и разрешения на MCP writes этот этап
не создаёт. Public MCP adapter, grants, CRUD/search/sharing/jobs не реализованы.

## Проверенная граница

- [Store](../../../crates/bazza-store/src/db.rs) сохраняет прежний `Store::open`
  для GUI, дополняя его ранним отказом от future schema. Service-aware API разделён
  на `LibraryOwnerGuard::acquire_existing` / `acquire_for_create`,
  `Store::open_existing_owned` и `create_owned`. Создание требует существующую
  директорию и новый DB file; `RequireCurrent` не мигрирует, `Upgrade` включается
  явно. Неверный existing path не создаёт библиотеку.
- [Canonical owner guard](../../../crates/bazza-store/src/owner.rs) удерживается
  внутри Store. Connection закрывается раньше guard, в том числе при ошибке
  initialization. Второй service-aware opener получает `OwnerBusy`; DB/lock links
  и Windows reparse points отклоняются. Старый GUI не знает advisory lock:
  stopped-owner snapshot и version interlock остаются условием этапа 3.
- `SUPPORTED_SCHEMA` выводится из append migration list. Valid future SQLite
  header проверяется bounded read до SQLite open: закрытая future WAL library
  не получает новые sidecars. При поддерживаемом/старом header используется
  обычное read-only SQLite с committed WAL. Проверен случай, когда DB header
  поддерживается, но WAL уже содержит future `user_version`; DB и существующий
  WAL сохраняются побайтово. SHM является coordination state SQLite, его полная
  неизменность для такого read не обещается. `immutable=1` не используется.
- [Core](../../../crates/bazza-core/src/lib.rs) сохраняет library ID под owner
  guard, создаёт новый epoch при open и отдаёт отдельную private metadata projection.
  Identity появляется после schema validation/migration; отсутствующая/неотмеченная/
  future library не получает identity или endpoint. Простой service start не
  запускает capture, recovery, model download, inference или cloud STT.
- [Transport](../../../crates/bazza-service-transport/src/lib.rs) использует
  bounded length-prefixed frames. На Windows проверены server/client PID и SID,
  protected pipe DACL для текущего пользователя/SYSTEM, reject remote clients.
  Это внутренняя OS-user application boundary; внешний MCP principal и его
  whole-library grant здесь не подменяются локальным пользователем.
- [RPC и client](../../../crates/bazza-service-client/src/lib.rs) проверяют API,
  schema range, API contract build identity, library ID/epoch, требуемые capabilities/
  fixture-only OS-user context, request correlation,
  bounded deadlines и expected reply kind. Endpoint публикуется атомарно; PID из
  discovery не считается аутентификацией без OS peer check. Timeout, EOF, partial
  frame, внешний drop/cancellation, неверные correlation/epoch/kind оставляют
  соединение непригодным к повторному использованию. SQLite/GUI fallback нет.
- [Host](../../../crates/bazza-service/src/lib.rs) удерживает repository на время
  listener/handlers, ограничивает clients, отклоняет операции до hello, expired
  deadlines и incompatible hello. Unknown method/invalid frame закрывает только
  соответствующее соединение. Graceful shutdown закрывает clients/listener и
  освобождает ownership; crash/restart сохраняет library ID и меняет epoch.

## Windows demand-start и независимость процесса

[Broker](../../../crates/bazza-service-client/src/broker.rs) сохраняет bounded
nonsecret setup intent до OS registration. Task definition проверяется по
текущему пользователю, executable/arguments, Interactive/Limited context, отсутствию
triggers и lifetime settings. PowerShell запускается из абсолютного системного
пути без окна. Старый build spec можно отозвать; несовместимая повторная
регистрация не затирает прежний spec. Setup operations сериализованы отдельным
guard. Без доступного verified broker возвращается ошибка; обычный child или
прямой Store opener не служат fallback.

Выполнен [настоящий broker experiment](../../../crates/bazza-service/experiments/windows-broker.ps1)
на новой disposable fixture с пробелами и кириллицей в пути. Результат:
**`one_owner_survived_launcher_tree_and_restarted`**.
Одновременные starter clients подключились к одному service owner, который
пережил `taskkill /T /F` собственного launcher. Typed IPC продолжил читать
synthetic metadata без GUI. Последующий restart сохранил library ID и сменил
epoch. Временная task удалена: **`task_removed=true`, `cleanup_errors=[]`**.

Evidence финального build: `.git/local-tests/20261102-mcp/service-broker-evidence-checked.json`.
SHA-256 проверенного service EXE:
`C42D240048F84E0E41F52DE50733848305BB3D4B9B4EA374E65DB9E4BFD8EAC9`.
Generated libraries, setup metadata, PID/epoch evidence и executables остаются
только в ignored local test directory. Эфемерные process IDs не являются частью
публичного контракта. Первая попытка стенда получила успешные ответы обоих
starter clients, но Windows PowerShell Process/ExitCode проверка не выставила
ready marker; исправлен launcher harness, приложение ради этого не менялось.
Повторные прогоны, включая итоговый build, прошли; неуспешный прогон также удалил
свою временную задачу без ошибок cleanup.

Это проверка текущего Windows desktop execution host. Она не доказывает поведение
всех версий Codex/Claude Code, logout/boot persistence или нативную macOS
совместимость. В phase-0 direct breakaway получил error 5; этот отказ не выдаётся
за независимый lifecycle. Здесь проверялся именно user-session Task Scheduler.

## Recording baseline и параллельная работа

Capture callbacks, STT policy, recorder/pipeline, UI commands и recording defaults
в рамках этого service increment не менялись. Изменения performance-сессии
сохранены. Data-dir selector `BAZZA_DATA_DIR` и его дополнительный тест принадлежат
параллельной задаче: это отдельный bounded opt-in выбор библиотеки, который нужно
учитывать в итоговом Store count и [testing guide](../testing.md).

Отдельный согласованный native Tauri test run из исходников до передачи native
slot и до opt-in data-dir selector дал **42 passed, 1 ignored**:

```powershell
cargo test -p bazza --release --lib --features tauri/custom-protocol --locked --offline
```
Ignored synthetic FFmpeg import затем выполнен отдельно: **1 passed** на более
позднем test EXE с SHA-256
`A2C5C6F1E4E019AB82E07B8B87C8B76B56E4B289A30F429BF0B65C67613AEBD0`
(`ffmpeg-recheck-sha256.txt` в local evidence directory). Это два build snapshots;
они не объявляются единым прогоном «43 passed». Ранее выполненные 41 UI tests и
Player/mock проверки описаны в linked baseline и не прибавляются повторно.

Открытие устройств, настоящий start/pause/stop capture, provider network/revoke,
полный crash/recovery waveform и decoder/asset-protocol playback не подтверждены
этими software tests. Ни fixture-only service, ни успешный native test harness
не разрешают подключение MCP mutations к рабочей библиотеке.

## Оставшаяся работа

Следующий data increment — этап 2: append schema/core, persistent revisions,
idempotency outcomes, actor provenance/change sequence, notes/transcript/summary
states, jobs/file lifecycle и search projection с проверками rollback/restart.
Production writes остаются закрыты до schema gates и GUI/worker cutover этапа 3.
Текущий private metadata transport ограничен 128 KiB; будущие public bodies до
1 MiB не следует пересылать через него без отдельного bounded transfer/limit
решения и тестов JSON escaping/UTF-8. Сейчас таких RPC методов нет.

macOS transport реализован, но не собирался и не запускался нативно в этой среде.
Реальные MCP SDK/stdio adapter и Codex/Claude Code acceptance относятся к этапам
7/10. Grants/secure credential pairing, public CRUD/jobs/search/sharing, worker
fencing, invalidation и production deployment ещё предстоят; M1–M11 целиком не
объявляются выполненными.
