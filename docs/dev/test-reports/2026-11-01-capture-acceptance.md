## Причина предупреждений о timestamps

8-секундная диагностика CPAL на устройствах без записи PCM показала:
89 из 801 mic packets и 1 из 799 system packets попадали в fallback только из-за
`callback < capture`. У обоих источников первый `callback` был ZERO; далее mic
callback snapshot иногда отставал от capture на 2–69 мкс. Реальная доставка
происходила спустя 10–20 мс после capture, а все native capture times проходили
проверку относительно QPC/монотонных часов. Остальные причины fallback не возникали.

CPAL 0.18.2/WASAPI получает эти значения из разных snapshots:
capture — [GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer),
callback — [GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition).
Исправлена проверка `CaptureClock`: используется capture относительно pre-play
anchor и монотонных часов; защиты ZERO/слишком старого/будущего времени сохранены.
Два новых теста воспроизводят stale/нулевой callback и действительно плохие метки.
Startup underrun/overrun наблюдался отдельно; сам по себе не доказывает потерю
содержимого записи, поэтому проверяется по медиа и маркерам.

Диагностика: `.git/local-tests/20261031-014043-clocks-health/native-clock-diagnostic-20261101/`.

## Другие исправления ошибок записи

- Отказ WAV writer выделен в `WriterError`: видимое сообщение и остановка с
  другого потока. Завершаются видео, forwarder, live ASR и captions, встреча
  сохраняется как `Failed`, доступные файлы остаются для восстановления.
- Публикационный barrier, проверка ID и сериализация start/stop защищают новую
  запись от старого auto-stop/завершающихся captions.
- `Recorder::drop` сигнализирует worker завершить WAV без блокирующего join.
- Обновление tray выполняется и при ошибке ручного stop. Сообщение об ошибке
  видеозахвата не обещает исправить повреждённый capture простым повтором mux.

Положительная A/V дельта означает, что звук наступает позже видеовспышки.
15 FPS даёт шаг 66.7 мс, детектор аудио — 5 мс; остаточные десятки миллисекунд
не используются как основание для фиксированной компенсации. Тест включает
проигрыватель FFplay и маршрутизацию звука. Человеческая речь не транскрибировалась.

В длинном тесте idle вырос с 402 до 773 с без ввода, при действующем AC display
timeout 300 с. Текущие записи больше не воспроизвели чёрное видео. Это подтверждает
защиту в данном сценарии; историческую причину каждого чёрного файла нельзя
доказать задним числом. Scoped power request проверен mock/нативным handle test:
System/Display очищаются, owned handle закрывается при drop, в том числе на другом
потоке. Системный план питания не изменён.

Все новые `mix.clock.json`, включая оба delay probes и четыре нормальных desktop
прогона, содержат `estimated_timestamps:false`. Mux сохраняет полную длительность
WAV; небольшое AAC padding не трактуется как потеря хвоста. Отсутствующие пары
строгого tone/flash detector сами по себе не считаются потерянными sample.

## Ограничения и завершение сессии

- Остаточная задержка в тестовой цепочке — десятки миллисекунд, в отдельных
  прогонах около 100 мс. Она не накапливалась и не повторяла длительность пауз;
  точность не объявляется нулевой или одинаковой для всех устройств.
- Испытаны текущие Windows/default devices и монитор 0. macOS, другие endpoints,
  смена устройств, длинный реальный разговор и качество STT/диаризации не приняты.
- WAV writer failure проверен контролируемой ошибкой файлового пути и unit-тестами
  состояния/сохранности; реальный диск не заполнялся. Отказ видеопроцесса проверен
  в desktop-приложении. Блокировку и ручной сон не вызывали.
- UI playback/seek новой сборки отдельно не повторены: окно свёрнуто, Computer Use
  остановил управление из-за пользовательского ввода. Медиа декодированы полностью;
  предыдущая baseline UI-проверка остаётся отдельным историческим результатом.
- Тестовый Hark завершён в idle, его дочерние capture-процессы остановлены, listener
  9222 закрыт. Восстановлено исходное отсутствие `%APPDATA%\Hark`/data pointer.
  Тестовая библиотека и диагностические файлы сохранены только под `.git/`.

Документация и текущий source checkpoint сохраняются локально. Следующая продуктовая
задача выбирается по roadmap; STT, настройки качества и новые функции этим исправлением
не объявляются выполненными.
