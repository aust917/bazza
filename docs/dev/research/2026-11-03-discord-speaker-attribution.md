# Имена говорящих из Discord в Bazza

3 ноября 2026 года · Техническое исследование

**Для серверного канала, куда можно пригласить бота, самый прямой путь к именным репликам — получать и транскрибировать отдельную аудиодорожку каждого Discord-аккаунта. Для обычной локальной записи Bazza стоит первым проверить Discord RPC.** Штатный настольный клиент умеет сообщать, кто начал и закончил говорить, а Bazza может сопоставлять эти события со своим аудио. Критическое условие — доступ Bazza к закрытому OAuth scope `rpc.voice.read`. Исследование опирается на документацию и исходники. Доступ от имени Bazza и точность на живом звонке предстоит проверить. [Discord RPC](https://docs.discord.com/developers/topics/rpc#speaking_startspeaking_stop), [OAuth scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes), [Craig](https://docs.craig.chat/).

## Какие данные решают задачу

| Что получает Bazza | Что можно показать | Где появляются ошибки |
| --- | --- | --- |
| Список участников | Кандидатов в меню переименования | Участие в канале ничего не говорит о конкретной реплике |
| События активности с `user_id` | Имена для реплик, совпадающих с однозначными интервалами | Перебивания, рассинхронизация и посторонний звук дают неоднозначность |
| Раздельные дорожки с `user_id` | Именной текст по каждой дорожке, включая одновременную речь | Потери пакетов, ошибки STT и несколько физических голосов в одном микрофоне |

Discord определяет аккаунт, который передал звук. Если у двух аккаунтов один ник, они остаются разными говорящими. Если один микрофон слышит двух людей, Discord видит один источник. Ключом сопоставления служит `user_id`, а читаемым именем — никнейм сервера, затем `global_name`, затем `username`. Сохранять стоит имя на момент звонка, отдельно от исправления пользователя. Никнейм меняется и может совпадать у разных аккаунтов. [Объект пользователя](https://docs.discord.com/developers/resources/user#user-object), [участник сервера](https://docs.discord.com/developers/resources/guild#guild-member-object).

## Локальный RPC штатного клиента Discord

1. Bazza подключается к IPC клиента Discord через именованный канал Windows или Unix-сокет macOS. Приложение использует собственный Discord Application ID, а пользователь проходит `AUTHORIZE` и `AUTHENTICATE`. Обычного входа через Discord с `identify` для голосовых событий недостаточно. [Транспорт и авторизация](https://docs.discord.com/developers/topics/rpc#rpc-over-ipc), [OAuth scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes).
2. `GET_SELECTED_VOICE_CHANNEL` возвращает текущий канал с данными голосовых участников. Bazza отслеживает `VOICE_CHANNEL_SELECT` и изменения `VOICE_STATE_*`, а на нужный канал подписывается на `SPEAKING_START` и `SPEAKING_STOP`. В документированном payload события речи есть `user_id`. Время начала звука в записи Bazza нужно вычислять на своей стороне. [Текущий канал](https://docs.discord.com/developers/topics/rpc#get_selected_voice_channel), [события речи](https://docs.discord.com/developers/topics/rpc#speaking_startspeaking_stop).
3. Адаптер ставит метку монотонных часов при получении события, ведёт интервалы отдельно по каждому ID и сопоставляет их с записанным аудио. Событие может прийти раньше или позже звука в WAV. При переключении канала или разрыве связи текущие интервалы закрываются как неполные, а новый список участников загружается заново. Серверный канал, личный звонок и групповой DM нужно проверять раздельно, включая собственный микрофон, push-to-talk и разговор при свёрнутом Discord.

Документация относит `rpc` и `rpc.voice.read` к доступу одобренных партнёров и описывает до 50 тестировщиков для RPC в разработке. Наличие тестового списка само по себе не подтверждает выдачу голосового scope новому приложению. Поэтому первый критерий — получить `SPEAKING_START/STOP` с собственным Application ID Bazza. Mynah использует OAuth с PKCE. При проверке нужно подтвердить, что этот flow доступен новому приложению, чтобы клиентская сборка обходилась без `client_secret`. В публичном трекере другого проекта разработчик сообщает об отказе в `rpc.voice.read`, так что доступ для более широкой аудитории следует рассматривать отдельно. [Ограничения RPC](https://docs.discord.com/developers/topics/rpc#restrictions), [OAuth scopes](https://docs.discord.com/developers/topics/oauth2#shared-resources-oauth2-scopes), [код авторизации Mynah](https://github.com/ba1lly/Mynah/blob/main/src/mynah/rpc.py), [опыт PQ Companion](https://github.com/jasonsoprovich/pq-companion/issues/150).

## Бот в голосовом канале

**Приглашение.** Для серверной установки нужен участник с `MANAGE_GUILD`, а боту — доступ к конкретному каналу и `CONNECT`. Он входит видимым участником с приёмом звука (`self_deaf=false`), при этом может держать свой микрофон выключенным. Установка приложения на пользователя даёт доступ к командам. Она не превращает бот-аккаунт в участника личного или группового звонка. Для пилота достаточно одного обычного серверного voice channel. Stage имеет отдельное поведение и требует самостоятельной проверки. [Установка Discord Apps](https://docs.discord.com/developers/quick-start/getting-started#choosing-installation-contexts), [разрешения](https://docs.discord.com/developers/topics/permissions), [подключение к голосу](https://docs.discord.com/developers/topics/voice-connections#connecting-to-voice).

**Привязка звука.** Обычный Gateway с `GUILD_VOICE_STATES` сообщает о входе, выходе и изменении состояния, включая mute. Отдельный Voice Gateway сопоставляет `SSRC` аудиопотока с `user_id` через opcode `Speaking`. Для границ реплик нужны пакеты соответствующего потока и, при необходимости, VAD по декодированному звуку. Один opcode может означать первое появление источника или смену состояния, а сами пакеты могут содержать тишину. При переподключении сопоставление потоков восстанавливается для новой сессии. Для имени достаточно данных участника из voice state или точечного запроса `Get Guild Member`. Запрашивать весь список сервера, `GUILD_MEMBERS` или доступ к содержимому сообщений для этой задачи не требуется. [Gateway intents](https://docs.discord.com/developers/events/gateway#list-of-intents), [Voice State](https://docs.discord.com/developers/resources/voice#voice-state-object), [Voice Gateway](https://docs.discord.com/developers/topics/voice-connections#speaking), [Songbird CoreEvent](https://serenity-rs.github.io/songbird/current/songbird/events/enum.CoreEvent.html), [Get Guild Member](https://docs.discord.com/developers/resources/guild#get-guild-member).

**Шифрование и библиотека.** С марта 2026 года обычные звонки требуют DAVE, протокол сквозного шифрования Discord. Бот участвует в той же защищённой сессии, что и другие участники. Для Rust первый кандидат — Songbird 0.6.x с `receive`, где `VoiceTick` даёт данные по `SSRC` и есть реализация DAVE-декодирования. Для Node быстрый стенд можно собрать на `@discordjs/voice`, но авторы отдельно предупреждают о стабильности недокументированного Discord audio receive, а открытый отчёт по 0.19.2 описывает проблемы с DAVE. Pycord 2.8.1 прямо предупреждает, что запись при DAVE может не сработать. Факт успешного входа бота нужно проверять отдельно от факта получения декодируемой речи нескольких пользователей. [Обязательность DAVE](https://discord.com/blog/every-voice-and-video-call-on-discord-is-now-end-to-end-encrypted), [Songbird 0.6.1](https://github.com/serenity-rs/songbird/releases/tag/v0.6.1), [приём пакетов Songbird](https://github.com/serenity-rs/songbird/blob/v0.6.1/src/driver/tasks/udp_rx/mod.rs), [discord.js Voice](https://github.com/discordjs/discord.js/blob/main/packages/voice/README.md), [отчёт о DAVE](https://github.com/discordjs/discord.js/issues/11653), [Pycord](https://docs.pycord.dev/en/v2.8.1/api/voice.html).

| Режим бота | Что передавать в Bazza | Что это даёт |
| --- | --- | --- |
| Только интервалы | ID, имя, активные интервалы и разрывы. В Songbird `DecodeMode::Pass` позволяет брать заголовки RTP. Для точной активности можно применять VAD к временно декодированным кадрам в памяти. [DecodeMode](https://serenity-rs.github.io/songbird/current/songbird/driver/enum.DecodeMode.html) | Подсказки для существующей записи. Сохраняется ограничение общего микса при перебиваниях |
| Именные дорожки | Отдельный поток или локальный файл на аккаунт с общей шкалой времени | Независимый STT для каждого говорящего и совмещение реплик на общей шкале. Повышаются требования к ресурсам и обработке дополнительного аудио |

Для локального пилота бот может работать отдельным процессом на компьютере пользователя. Он получает голос от Discord и отдаёт Bazza события через локальный IPC. Discord уже доставляет аудио участникам звонка, а отдельный облачный сервер Bazza здесь не нужен. Бот на удалённом хосте добавил бы ещё одно место обработки данных. Для режима с дорожками важно использовать RTP-время внутри каждого потока и общий якорь на стороне приёмника. У разных SSRC свои RTP-часы. Время первого пакета годится как начальная оценка, которую нужно сверять с записью и проверять после reconnect. [Voice transport](https://docs.discord.com/developers/topics/voice-connections#transport-encryption-and-sending-voice), [OpenRecapper](https://github.com/The-Yak-Collective/openrecapper/blob/main/src/workers/voice-worker.ts#L239-L255).

## Как связать это с записью Bazza

Сейчас Bazza примерно раз в 45 секунд собирает имена из найденного окна и добавляет их к списку участников. Сбор работает на Windows и возвращает строки без ID и интервалов речи. Аудио пишется в `mix.wav` и отдельные `mic.wav` и `sys.wav`, когда соответствующие источники доступны. После звонка диаризация назначает каждому сегменту транскрипта один акустический кластер и отдельно подбирает профиль из Voices. R1 требует сохранять микрофон и весь системный звук, включая видео и другие приложения. Дорожки Discord можно использовать как дополнительный источник для имён или распознавания Discord-реплик, привязанный к полному архиву Bazza. [R1](../../product/requirements.md), [сбор участников](../../../src-tauri/src/recorder.rs), [аудиозахват](../../../crates/bazza-capture/src/recorder.rs), [обработка спикеров](../../../src-tauri/src/pipeline.rs), [ограничения захвата Craig](https://craig.chat/faq/).

1. **Собирать наблюдения только в активной записи.** Оба адаптера могут отдавать один контракт с источником, локальным ID сессии, ID аккаунта, отображаемым именем, началом и концом активности и разрывами покрытия. Сбор отделён от capture callback. Паузы вырезаются по шкале активной записи, чтобы задержка из реального времени не сдвигала реплики после возобновления. Остановка, смена канала и потеря источника закрывают предыдущую подписку.
2. **Привязывать имя после сопоставления нескольких реплик.** Учитывать покрытие кластера, долю однозначных пересечений и преимущество перед вторым кандидатом. Задержку событий откалибровать по коротким контрольным фразам. Для локального владельца учитывать дорожку микрофона и отдельно измерить случаи, когда Discord его замьютил, а Bazza продолжает писать. При двух говорящих, дыре в событиях или конфликте с Voices оставлять нейтральную подпись либо показывать подсказку для проверки. Системное аудио может включать видео и музыку, совпавшие по времени с событием Discord.
3. **Хранить происхождение имени и решение пользователя раздельно.** Подпись «Из Discord» полезна рядом с возможностью исправить имя. Подтверждённые пользователем правки имеют приоритет при повторной обработке. Матч по Discord ограничен встречей. Добавление образца в Voices остаётся отдельным действием. Привилегированные токены, сырые внешние ID и журналы активности не нужны в саммари, webhook или экспорте. Публичные подписи и имена требуют обычных правил выбранного пользователем экспорта. [R4 и R5](../../product/requirements.md), [Voice memory](../voice-memory.md), [Privacy Bazza](../../privacy.md).

События речи отвечают на вопрос «кто мог произнести этот фрагмент». Если ASR склеил длинную реплику и короткое «да» в один caption, смену говорящего удастся показать только при наличии надёжных временных меток слов или отдельного распознавания дорожек. Один общий звук может содержать две одновременные реплики, из которых STT разберёт лишь одну. Поэтому именованные интервалы и раздельный STT стоит сравнивать по разным метрикам. [Текущая привязка одного кластера к caption](../../../crates/bazza-diarize/src/merge.rs), [предыдущее исследование говорящих](../../product/2026-11-02-speaker-recognition-research.md).

## Пилот и критерии выбора

| Шаг | Что измерить | Как принять решение |
| --- | --- | --- |
| **1. RPC на Windows** | Получение scope и событий со своим Application ID. Серверный канал, DM, групповой DM, два одновременно говорящих, свёрнутое окно, mute и reconnect | Если голосовой scope выдан и события приходят стабильно, делать источник подсказок без бота. Если scope недоступен, у серверного пилота остаётся бот |
| **2. DAVE-приёмник в тестовом сервере** | Три тестовых аккаунта, включая одинаковые ники, короткие ответы, одновременную речь, вход во время фразы и повторное подключение. Проверять декодируемый звук и `SSRC → user_id` отдельно | Если потоки устойчивы, прогнать те же реплики в режиме интервалов и в режиме отдельных дорожек |
| **3. Сравнение с обычной обработкой Bazza** | Разметить истинного автора каждой реплики. Измерить точность среди подписанных реплик, долю подписанных, ошибку временных границ и долю правильно подписанных коротких ответов. Отдельно посчитать слова с неверным именем, одновременную речь и посторонний системный звук | Подбирать пороги на одной серии, проверять на другой. Для первого пилота ориентир — ≥98% точности среди автоматически подписанных неперекрывающихся реплик при ≥80% покрытии в поддерживаемом канале. Это предлагаемые критерии, а не измеренный результат |
| **4. Проверка жизненного цикла** | Пауза, возобновление, смена канала, длинный звонок, потеря соединения, ручное исправление, повторная обработка. Проверить macOS после Windows | Разрыв переводит источник имён в недоступный. Запись продолжает идти, пропуски и ручные правки сохраняются корректно |

Для пилота нужны добровольные участники и явный старт записи. Боту стоит показывать состояние записи в канале и сообщать об окончании. Токен бота остаётся у локального процесса. Условия Discord для API Data предусматривают ограничение цели сбора, удаление данных, шифрование при хранении и условия передачи третьим сторонам. Для первого теста достаточно держать необработанные метаданные и декодируемый звук локально на время проверки. Облачный STT для полученного ботом аудио потребует отдельно проверить применимость этих условий к данным и выбранному провайдеру.
