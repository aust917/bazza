# Измерения для приёмки Meet и Discord

Запускайте из корня Bazza. Нужны Python 3, FFmpeg с libx264 и NumPy для разбора
записи. Для обработки уже собранного JSON достаточно стандартной библиотеки
Python. Храните тестовые видео, WAV, расшифровки и отчёты в локальной тестовой
папке вне отслеживаемых Git файлов.

## Запись контрольных меток

```powershell
python -B tools/bazza-call-acceptance/measure/media_evidence.py reference <marker.mp4> <markers.json> --duration-ms 1800000
```

Откройте ролик в отдельном видимом окне на записываемом экране. Оставьте
неперекрываемый прямоугольник внутри чёрного/зелёного поля. Источник звука
ролика должен попадать в фактически выбранный захват звука ПК. Запустите Bazza,
затем воспроизведите ролик один раз с начала и остановите запись после последней
метки. Голосовые боты параллельно воспроизводят свой сценарий в звонке. Звуковые
метки этого ролика проходят через локальный захват, поэтому проверка A/V
не зависит от сетевого пути Meet или Discord.

Для короткого прогона задайте длительность ролика под сценарий. Длинный ролик
содержит по семь пар меток в начале, середине и конце, с разной фазой
относительно кадров записи. Сам ролик генерируется с известными PTS и подходит
для проверки детектора. Для вывода о Bazza нужен MP4, записанный самим Bazza.
Прямоугольник `--roi` задаётся в пикселях **готового видео**, в порядке
`x,y,ширина,высота`. Сверьте его по одному кадру с зелёной вспышкой.

## Разбор записанного видео

```powershell
python -B tools/bazza-call-acceptance/measure/media_evidence.py observe <Bazza-video.mp4> --marker-source <markers.json> --roi 32,32,24,24 --manifest <scenario.json> --schedule-offset-ms 5000 --output <evidence.json>
```

Подставьте фактические координаты. В примере запуск реплик начался около пятой
секунды записи. Это лишь центр поиска в аудио. Измеренные времена берутся из
записанного MP4, включая задержку голосовой платформы. По умолчанию окно
поиска составляет ±5 секунд. При известном переподключении или более позднем
старте его можно расширить через `--search-ms`.

Для A/V анализатор извлекает аудио и PTS кадров на общей шкале MP4.
Каждому тону 1 кГц должна соответствовать вспышка с проверяемым порядком и
интервалами из `markers.json`. При неоднозначной паре автоматический результат
остаётся без оценки. Границы A/V учитывают длительность предыдущего кадра и
точность детектора аудио. При 15 FPS соседние кадры разделены примерно 67 мс.
Для дрейфа сравниваются окна начала и конца, разделённые минимум 29 минутами.
Пограничный результат остаётся неопределённым, если интервал измерения
пересекает допуск.

Для реплик анализатор ищет каждый исходный WAV в звуковой дорожке готового
видео. В границы начала входят разница между оценкой Soniox и началом устойчивой
энергии в WAV, а также погрешность детектора. Порог срабатывания на энергию
может включить вдох, поэтому для спорных реплик проверьте начало речи на слух
с визуализацией формы волны и уточните поля `start_ms`, `start_low_ms`,
`start_high_ms` на шкале самого MP4. При сильном перекрытии, пропавшем звуке
или искажении кодеком анализатор может оставить реплику в `unresolved_phrases`.
Подставьте независимое наблюдение после прослушивания записи. Если начало
невозможно установить, оставьте реплику без отметки.

## Проверка текста и кликов в плеере

Используйте JSON `participant-transcript.json` той же встречи и провайдера.
Поле `segments` содержит `speaker_id`, `speaker_name`, `start_ms`, `end_ms`
и `text`. В именном тексте `start_ms` и `end_ms` относятся к дорожкам бота.
С видео сравниваются `playback_start_ms` и `playback_end_ms`. Пропущенная
привязка остаётся без оценки. Если соответствие тестовых имён не однозначно,
добавьте отдельный JSON вида `{"<ID дорожки>":"<participant.id из scenario.json>"}`.

Дополните JSON наблюдений полями, которые собираются через реальный плеер и
при разборе неоднозначного текста.

- `seeks` содержит объекты `{"id":"<utterance.id>","seek_ms":12345}`. В режиме
  видео кликните по реплике и зафиксируйте фактический playhead после завершения
  перехода, например `currentTime` видеоэлемента при событии `seeked`.
  Проверьте не менее трёх реплик из разных частей записи, включая реплику
  после переподключения, если оно было. Не копируйте таймкод расшифровки в
  наблюдение. Если доступен только округлённый индикатор плеера, его точности
  может не хватить для порога в 300 мс.
- `assignments` содержит объекты
  `{"id":"<utterance.id>","segment_indices":[0,1]}`. Нумерация начинается с нуля
  в исходном массиве `segments`. Заполняйте для вручную проверенного
  соответствия, когда распознавание разбило или сильно изменило реплику.
  Автоматический поиск учитывает текст, включая последовательность сегментов,
  и не подбирает совпадение по близости таймкодов.
- `expected_bot_absent_ids` — идентификаторы реплик, которые заведомо пришлись
  на проверенное окно отсутствия бота. Сверьте это окно с журналом входа и
  отдельно подтвердите, что запись ПК продолжалась. Исключайте только
  предусмотренные сценарием интервалы с доказанной причиной отсутствия.

```powershell
python -B tools/bazza-call-acceptance/measure/measure.py meet <scenario.json> <evidence.json> <participant-transcript.json> --speaker-map <map.json> --output <score.json>
```

Для другого режима используйте `discord`. Отчёт содержит смещения каждой
реплики, покрытие, ошибки атрибуции, дубли контрольных фраз и оценку частоты
ошибок слов на сопоставленных и пропущенных репликах. Допуск p95 абсолютной
ошибки A/V составляет 80 мс, для начала реплики и перехода по ней — 300 мс.
Для сессии от 30 минут допуск дрейфа составляет 50 мс за 30 минут. Exit code
`0` означает прохождение требуемых порогов, `1` — измеренное нарушение, `2` —
недостаточные, неоднозначные или некорректные данные. Короткий прогон не
подтверждает 30-минутный дрейф. Ошибку конца фразы отчёт показывает отдельно.

Программные проверки измерителя:

```powershell
python -B -m unittest discover -s tools/bazza-call-acceptance/measure -v
```
